# graphersal-server 0.3.0 (unreleased)

**EXPERIMENTAL.** Everything here (commands, files, routes, answers) may change without notice
in later versions. This is a draft: it grows with every change until the release.

**Upgrading from 0.2.0:** `serve` and the console now refuse a server directory that is not
private to its owner. A directory made by 0.2.0 usually has `sessions/` (and maybe the
directory itself) open to group or others: run `graphersal-server init DIR` once as the
directory's owner; it tightens the modes and lists them under `owner only`. The error of a
refused command names the exact `chmod`/`chown` too.

**Upgrading: MCP exposure.** New databases and aliases are now hidden from MCP by default (see
"MCP off by default" below). An upgraded server directory keeps what it offered: its databases
and aliases have no entry in `mcp.toml`, and a name without an entry stays offered (the old
rule); a directory without `mcp.toml` keeps MCP on. Only names created after the upgrade are
hidden, unless `graphersal-server mcp expose-new on` restores the old behaviour for them.

## Safe concurrent changes

Many browsers (and scripts, and the console) may change the server at the same time; the files
stay whole and every acknowledged change stays
([The Server Directory](../reference/server_directory.md#concurrent-changes)).

- **Atomic writes with their own temporary file.** Every configuration file (`access.toml`,
  `aliases.toml`, `database.toml`, `server.run`, the session files, `models/models.toml`,
  backup sidecars) is written to a temporary file of its own (`<file>.tmp-<pid>-<n>`; 0.2 used
  one fixed `<file>.tmp` per file), flushed to the disk, renamed into place, and on unix the
  directory is flushed too (the new file survives a power loss). Temporary files a crash left
  behind are removed at the next start (only names the server makes).
- **Locks held across read, change and write; memory only after the write.** Fixed on the way:
  the grants of a deleted database or a removed alias are now dropped in the same step as the
  name (before, a new database or alias of that name made in between could lose the grants it
  had just been given); a grant is written while its database or alias is known to exist (it
  could land on a name deleted at that moment); `user admin NAME on|off` reads and changes the
  roles in one step (a concurrent role change is no longer undone); the `grantsRemoved` count of
  a user removal is taken in the same step. The lock order is documented.
- **Revisions against lost updates.** Users and grants (`access.toml`), aliases
  (`aliases.toml`) and each database's settings (`database.toml`) carry a `revision`: `GET
  users`, `GET grants`, `GET aliases` (also as `ETag`), `aliasesRevision` of `GET databases`,
  and `revision` in every database entry. A change may send the revision it is based on (body
  field `revision` or `If-Match`); when someone else changed the object meanwhile it is refused
  with `409 {"error", "help": "changed by someone else: reload", "revision": <current>}` and
  nothing changes. Without a revision a change is applied as before (the console, scripts,
  older clients). Checked: every users and grants change, alias set/flip/rename/remove, read-only
  and auto-load ([Admin API](../reference/admin_api.md#revisions-concurrent-changes)).
- **Web UI:** the Users tab, the alias dialogs and remove, and the read-only and auto-load
  toggles send the revision of what they show; on a `409` the tab shows a warning (the server's
  text and help, and that the tab now shows the current state) and reads its data again.
- The library: `revision` (`of`, `check`, `from_if_match`, `etag`, `CONFLICT_HELP`),
  `ServerError::Conflict`, `Admin::expecting`, `Access::edit` (`AccessEdit`, with `set_admin`),
  `Access::revision`, `AccessFile::revision`, `DatabaseEntry::revision`,
  `Registry::aliases_with_revision`, `aliases_revision`, `alias_remove_with`, `delete_with`,
  `set_read_only_expecting`, `set_auto_load_expecting`, `Loader::set_read_only_expecting`,
  `ServerDir::remove_stale_temps`; `Registry::alias_set_with` and `alias_rename_with` take the
  expected revision.

## The server directory is the boundary

The OS user owning the server directory is the operator (PostgreSQL's peer-authentication
model): whoever can write the directory could edit `access.toml` or read the operator token
anyway, so the console needs no credentials there. 0.3.0 enforces that the directory really is
private ([Security Model](../guide/security.md#the-directory-owner-is-the-operator)):

- **`init`** creates the directory with mode `0700`, `sessions/` with `0700` and the secret
  files (`access.toml`, `server.run`, `sessions/*.json`) with `0600`; every later write keeps
  these modes. On an existing directory owned by the current user it tightens the modes it
  finds too open (`owner only` in its output).
- **`serve` and every console command** (`db`, `import`, `models`, `user`; offline and through
  a running server with the operator token) refuse, with exit code 1, a directory or file
  owned by another OS user (root on another user's directory included), a directory,
  `server.toml` or `aliases.toml` writable by group or others, and a secret (`access.toml`,
  `server.run`, `sessions/` and its files) readable or writable by group or others. The error
  lists every problem and the command fixing it (`chmod 600 ...`, `sudo -u OWNER ...`,
  `sudo chown -R ...`).
- **Windows:** no check (it would need the Win32 security API); the directory's ACL is the
  boundary.
- **Audit:** the operator's records name the OS user, `actor="operator (os:<name>)"`: the
  console's own user offline, and the user the server runs as for the operator token through
  the server. An offline console command logs its audit lines on stderr when `RUST_LOG` is set
  (`RUST_LOG=graphersal_server::audit=info`).
- **`--token TOKEN`** (or `GRAPHERSAL_SERVER_TOKEN`) for `db`, `import`, `models` and `user`:
  the command goes to the running server with that user's admin token (address `--server
  ADDRESS`, else the directory's `server.run`) and touches no file of the directory, so the
  permission checks do not apply; the audit names the token's user. Without a running server
  it is refused. `--server` without a token is a usage error.

## start, stop and status

A server in the background without hunting for its pid:

- **`graphersal-server start --dir DIR [serve options] [--timeout SECS]`** spawns `serve` as a
  detached process (Unix: a new session, no controlling terminal; Windows: `DETACHED_PROCESS |
  CREATE_NEW_PROCESS_GROUP`, no fork), stdin closed, stdout and stderr appended to
  `DIR/logs/server.log` (new: `logs/` mode `0700`, the log `0600`). It waits until the server
  answers `GET /readyz` (at most SECS, default 60), then prints the usual start block on
  stderr and the address line on stdout, and exits 0. A directory without `access.toml` gets
  its first admin from `start` itself, so the token is printed once on the terminal and never
  written into the log. Refused while a server runs on DIR (naming its pid and URL); a server
  that exits before it is ready, or is not ready in time, is exit code 1 with the last lines of
  its log (one still starting after the timeout keeps running, and the error says so).
- **`graphersal-server stop --dir DIR [--timeout SECS]`** asks the running server to stop
  through the new operator-only route `POST /api/admin/shutdown` (with the operator token of
  `server.run`); the server answers `202` and stops exactly as on Ctrl+C. On Unix, when the
  API cannot be reached, it falls back to SIGTERM (the same clean stop). It waits until
  `server.lock` is released (default 60 s; after that the error names `kill`/`taskkill`) and
  prints `stopped`. Without a server it prints `not running` and exits **0** (as LSB init
  scripts do for stopping a stopped service); a stale `server.run` a crashed server left is
  removed and named.
- **`graphersal-server status --dir DIR [--json]`**: running or stopped, the pid, address,
  version, uptime, databases (count, loaded ones by name), memory (the ceiling; the live heap
  is not measured by this build) and the log; a stale `server.run` is reported, not removed.
  Exit code **0** running, **3** stopped (the LSB convention).
- `stop` and `status` also take `--token TOKEN [--server ADDRESS]` like the other console
  commands.
- New admin routes: `GET /api/admin/server` (the server's facts, any admin) and `POST
  /api/admin/shutdown` (the operator or an admin user; `403` for `everyone` with access
  control off; audited). `server.run` gains `started_at_ms`.
- The library: `ServeOptions::with_stop_hook(StopHook)` (what the shutdown route calls; `serve`
  routes it into its Ctrl+C channel), `graphersal_server::daemon` (`start`, `stop`, `status`
  and their `--token` forms), `ServerError::Service`, `AuditEvent::ShutdownRequested`.
- The `serve` start block's `stop` row names `graphersal-server stop --dir DIR`.
- Under systemd or launchd run `serve` in the foreground: examples in
  [Running as a Service](../guide/service.md).

## Shorter names for new databases, aliases and users

- **A NEW name** (create, clone, import by upload, path or inbox, restore into a new name, a
  new alias, alias rename, user add; console, admin API and web UI alike) has **at most 32
  characters** (was 63), **ends with a letter or digit** (no trailing `-`, `_` or `.`) and
  holds **no `..`**; the rest is unchanged (`[a-z0-9]` first, `[a-z0-9._-]` inside, no Windows
  device names, `jobs` reserved for databases and aliases). A refusal is `400` (console: exit
  code 1) with `invalid name "<name>": <reason>`, one reason per check.
- **Existing names keep working:** a database, alias, user or grant named by 0.2.0 under the
  older rule (up to 63 characters, a trailing `-` or `_`, `..` inside) is still loaded,
  served under `/db/<name>/`, looked up, granted, flipped (an alias) and backed up; its backup
  restores over it and, after the database was deleted, under its own name again (which a
  `jobs` database made before 0.2.0 now may too). Only a restore into ANOTHER name takes the
  new rule.
- **Web UI:** every field where a new database, alias or user name is typed (create, clone,
  import, restore into a new database, alias, alias rename, add user) shows the rule under it
  (*Up to 32 characters: lower-case letters, digits, '.', '_' and '-'; starts and ends with a
  letter or digit.*) and checks it before sending, with the server's own error text. The name
  suggested from an import file is always a valid new name (cut to 32 characters, `..` made
  one dot, no trailing `-`/`_`/`.`), and the default name of a restore into a new database
  (`<name>-restored`) is shortened to fit.
- **Windows:** the short names keep paths under the server directory short; keep the server
  directory itself short too (`MAX_PATH` = 260 characters unless long paths are enabled;
  [The Server Directory](../reference/server_directory.md#databasesname)).
- The library: `names::MAX_NAME_LEN` is 32; new `names::MAX_EXISTING_NAME_LEN` (63) and
  `names::validate_new_user_name`; `validate_new_name` checks the new rule; `validate_name`
  stays the rule of existing names; `Registry::prepare_tmp_former_name` (a restore under the
  deleted database's own name).

## Grants on aliases

0.2.0 refused a grant on an alias (`409`: grant the database). 0.3.0 takes it
([Users, Tokens and Grants](../guide/access.md#grants-on-aliases)):

- **Through the alias only:** a grant on an alias reaches the database the alias names NOW, but
  only when the request names the alias: `/db/<alias>/...`, MCP `use_graph <alias>` (or
  `"graph": "<alias>"`), the alias's row in the server-wide `/mcp` `list_graphs` and in "My
  databases". The real name stays hidden without a grant of its own (`404`, `401` for
  anonymous; not listed as a database). The level through the alias is the higher of the grants
  on the alias and on its database, capped by the database's mode. `*` grants are unchanged.
- **Flip:** pointing the alias at another database moves the access at once, also for open MCP
  sessions that selected the alias.
- **Rename:** `db alias rename OLD NEW` (and `POST /api/admin/aliases/<alias>/rename`) moves the
  grants on OLD to NEW in `access.toml` (answer `grantsMoved`; the console prints `grants moved`
  when there were any; audited as `GrantsMoved`).
- **Remove:** `db alias remove ALIAS` (and `DELETE /api/admin/aliases/<alias>`) removes the
  grants on the alias too (answer `grantsRemoved`; each audited as a revoked grant), so a later
  alias or database of that name inherits nothing.
- **Every grant listing marks the name:** the admin API's grant objects (in `GET users`, `GET
  grants`, `POST grants` and each user's `grants`) gain `kind` (`database`, `alias`, `all` for
  `*`, `missing` for a name that names nothing now) and `target` (the alias's current
  database, else `null`); `GET /api/databases` rows gain `kind` (`database` or `alias`).
  `graphersal-server user list` shows `prod → prod-2026-11 (alias)` and `gone (missing)`, and
  `user grant` on an alias says which database it reaches now. Web UI: the Users tab's grant
  tables show `prod → prod-2026-11 (alias)`, its database picker offers the aliases too (marked,
  after the databases), and "My databases" shows `alias → <database>` or `database` beside each
  name.
- **Grants never outlive their name** ([Users, Tokens and Grants](../guide/access.md#grants-never-outlive-their-name)).
  0.2.0 (and the first 0.3.0 builds) kept the grants of a deleted database in `access.toml`, so
  they applied again to whatever took the name later: a new database, an alias, a rename onto
  it. Now:
  - `db delete` (and `DELETE /api/admin/databases/<name>`, the Databases tab) removes every
    grant on the database, each audited as a revoked grant; the answer gains `grantsRemoved`,
    the console prints `grants removed: N (a restore does not bring them back)` when there were
    any, and the web UI's notice names them (its delete confirmation says so too).
  - A restore does not bring grants back (the Backups tab's restore form and the console's
    restore note say so); a restore over an existing database keeps its grants.
  - Grants still left on a name (from 0.2.0 or a failed rewrite of `access.toml`) are removed
    first when a new database or alias takes the name (create, clone, import, a restore into a
    new or a deleted database's name, a new alias, the new name of an alias rename), audited
    each; the answer gains `leftoverGrantsRemoved` (only when > 0), the console prints a
    `warning:` line and the web UI a warning notice. A failure to rewrite `access.toml` there
    refuses the operation. Until then such grants stay listed as `missing` and revocable.
  - The library: `Deleted::grants`, `Imported::leftover_grants`, `Restored::leftover_grants`,
    `Renamed::leftover`; `Admin::create_reported`, `Admin::clone_reported` (the entry and the
    leftover count); `Admin::alias_set` answers the leftover count (was `()`);
    `Registry::alias_set_with`, `Registry::alias_rename_with` (a `claim` run under the
    registry's write lock).
- The library: `AccessFile::granted_level_via`, `grants_on`, `rename_grants`, `drop_grants`;
  `Access::reach`, `granted_level_via`, `rename_grants`, `drop_grants` (`level_in` counts an
  alias's own grants); `Admin::alias_remove` answers the number of grants removed;
  `Renamed::grants`; `AuditEvent::GrantsMoved`.

## The web UI shows the current state, sorts every table, explains bases

- **Fresh data on every visit.** Every tab of every UI profile (the admin tabs, "My databases",
  the sign-in page's open databases) reads its data again each time it is shown, and when the
  window gets the focus back or the page becomes visible while it is shown. Before, the
  playground kept a tab alive with the data of its first visit: a user added with
  `graphersal-server user add` (or in another browser) did not appear in Users until the page
  was reloaded. A refresh replaces only the shown data; an open dialog or form keeps its input.
  The Runs tab's 2-second poll stops while another tab is shown.
- **`Cache-Control: no-store` on every answer**, exactly once: the root, user and admin API
  (also refusals, unknown routes and redirects), each database's API and the UI files. Answers
  that named it twice (`GET /api/databases`, a `401`, login and logout) name it once now.
- **Sortable columns** on every table (databases, aliases, users, grants, backups, the import
  inbox, models, databases waiting for a model, runs, "My databases"): click a header for
  ascending, again for descending (indicator and `aria-sort`); text in natural order, sizes,
  durations and ids by number, dates by time, missing values last, stable; the choice is kept
  per table in the browser (localStorage). The import inbox rows carry `bytes` for it.
- **Bases and layers explained.** The confirmation of "Promote to base…" and its tooltip say
  what a base is (a frozen, read-only database that layers are built over; each layer stores
  only its own changes), that promotion is one way and forever, and when to use it; the
  Databases tab's Kind column and the Backups tab's Kind column explain each kind in a tooltip,
  and a "Bases and layers" box under the database table sums it up.

## Disk and memory in the Databases tab, `db list` and `status`

- **Two size columns.** The Databases tab and `db list` show "On disk" (the database's
  directory: Store snapshots, journal, models; measured at most once per 5 seconds per
  database) and "In memory" (a loaded database's graph: the engine's footprint; a layer's own
  changes, its shared base in the tooltip). Both sort numerically (a database that is not
  loaded sorts last); the cells read `1.5 MB` with the exact bytes in the tooltip. The listing
  rows of the admin API gain `memoryBytes` (`null` when not loaded) and, for a loaded layer,
  `sharedMemoryBytes`. Before, the listing had only `sizeBytes`.
- **A memory summary** above the database table, in `graphersal-server status` (and its
  `--json`) and in `GET /api/admin/server`'s `memory`: the server process's resident memory
  (RSS; Linux, macOS and Windows), the loaded databases (each graph once: a base shared by
  layers counts one time), the machine's total and available memory, the memory limit in
  effect with where it comes from (`configured`, a container's `cgroup` limit, 80 % of the
  `physical` memory, `none`) and the `[limits] memory_limit`/`memory_headroom` settings, and
  what is free: the limit minus the process's memory, but never more than the machine's
  available memory (then `freeBasis: "machine-below-limit"`), or the machine's available
  memory without a limit. Before, `status` showed only the limit (`liveBytes`, `limitBytes` and
  `availableBytes` stay in the answer). No new dependency on Linux and macOS (`libc`);
  `windows-sys`, already in the tree, gives the Windows figures.

## The MCP tab: switch MCP, hide or protect databases, see its use

MCP started with the server and nothing switched it at runtime. Now (web UI tab **MCP**, the
admin API `GET`/`PUT /api/admin/mcp` and `PUT /api/admin/mcp/databases/<name>`, the console
`graphersal-server mcp status|on|off`, `mcp db NAME on|off`, `mcp db NAME read-only on|off`),
with no restart:

- **MCP on or off for the whole server.** Off: `/mcp` and every `/db/<name>/mcp` answer `503`
  with help at once, to every request, also those of agents connected before; their MCP
  sessions are not ended, and when MCP is switched on again they continue with the same
  session id and selected database, without a new `initialize`.
  `server.toml [mcp] enabled = false` stays the hard switch (no endpoint until a restart).
- **Per database or alias: offered to MCP or hidden.** A hidden name is not listed by
  `list_graphs`, answers `use_graph` and `"graph"` like an unknown name, and its
  `/db/<name>/mcp` answers `404`; the HTTP API is not affected.
- **Per database or alias: read-only for MCP.** MCP sessions only read it, whatever their grant
  (the HTTP API still follows the grant): the effective MCP level is the least of the grant, the
  database's mode and this switch. An alias narrows its database, never widens it.
- **Usage statistics** since the start (in memory, reset by a restart): open MCP sessions per
  user and per database, tool calls in total, per tool, per user and per database with their
  errors, the last 50 tool errors, and the requests refused while MCP was off; the tab shows
  them in sortable tables, fresh on every visit, beside the endpoint URL and the `claude mcp
  add` command with a placeholder token.
- The switches live in the new file `mcp.toml` of the server directory (written atomically by
  the server, with a `revision`: a change based on a stale page is refused with `409` and the tab
  reads the state again; checked by `serve`'s permission check like `aliases.toml`). A renamed
  alias keeps its settings; a deleted database or removed alias loses them. Changes are audited.

## MCP off by default: a new server, a new database, a new alias

Before, a new server answered MCP at once and every database or alias was offered to MCP the
moment it existed. Now nothing reaches MCP unless an admin lets it:

- **`init` makes a server with MCP switched off** (`mcp.toml`: `enabled = false`, `expose_new =
  false`; `init` says so and names `graphersal-server mcp on`). `server.toml [mcp] enabled`
  stays `true`, so the MCP tab or `mcp on` switches MCP on without a restart.
- **A new name is hidden from MCP.** Every database the server creates (create, import, clone,
  a restore into a new name, repair) and every new alias gets `exposed = false` in `mcp.toml`
  at birth, unless created with "expose through MCP": `--mcp` on `db create`, `db clone`, `db
  alias set`, `db restore` and `import`; `"mcp": true` in the admin API (`?mcp=true` for an
  upload import); the "Expose through MCP" checkbox of the web UI's create, clone, new alias and
  import forms. `--no-mcp` / `"mcp": false` hides it whatever the default. The answers carry
  `mcpExposed`, the console prints the `mcp db NAME on` command for a hidden name, the web UI's
  notice says "Not offered to MCP (expose it on the MCP tab)".
- **A server-wide default** decides for names created without saying: `mcp.toml`'s `expose_new`
  (default `false`), the MCP tab's checkbox "Expose new databases and aliases", `PUT
  /api/admin/mcp {"exposeNew": bool}` (audited), `graphersal-server mcp expose-new on|off`;
  `mcp status` shows it. Names there keep their settings when it changes.
- **Kept:** a restore over a database, a promotion and a swap keep the name and its setting; a
  renamed alias carries its setting; an alias flip keeps the alias's setting.
- **Upgrade rule:** a name without an entry in `mcp.toml` is offered, as before. A server
  directory made by an earlier version therefore offers exactly what it offered; a missing
  `mcp.toml` still means MCP on. A database copied into `databases/` by hand has no entry
  either: hide it with `graphersal-server mcp db NAME off`.

## Database settings: see and change a database's parameters

A database had many parameters (`database.toml`, its Store, its grants, MCP settings, backups)
but no place to see them together, and its description and query limits could only be set by
hand in `database.toml`. Now:

- **The Database settings tab** (web UI; "Settings…" on every row of the Databases tab opens it
  for that database, or pick one) shows everything about one database, grouped: identity (name,
  kind plain/layer, role normal/base, a layer's base, a base's layers, the aliases naming it,
  created), state and sizes (state, on disk, in memory), the query limits (per key: the
  database's own override, the server's default, what the next load uses, where it comes from,
  and while loaded what it runs under now), its MCP settings (link to the MCP tab), the grants
  on it, on aliases naming it and on `*` plus the admins (link to the Users tab), its backups
  (count, size, the latest; link to the Backups tab) and the Store's creation parameters,
  read-only (store id, damage policy, chunk size, creation time, backend, format version, last
  commit). Its tables sort; it reads the database again on every visit.
- **Edit in place:** the description, read-only, auto-load and each query limit override (set
  or clear; checked like `server.toml`: whole numbers, `0` = no limit, `max_value_depth` 0 = the
  default 128). Description and auto-load apply at once (auto-load at the next start), read-only
  at once also for a loaded database, a limit at the database's **next load**: the tab says so,
  marks the limits that differ from the running session and offers "Unload and load now…".
- **Admin API:** `GET /api/admin/databases/<name>/settings` (also by an alias) and `PUT
  /api/admin/databases/<name>/settings {"description"?, "readOnly"?, "autoLoad"?, "limits"?:
  {key: n | null}, "revision"?}`: one atomic write of `database.toml`, based on its revision
  (`409` when someone changed it meanwhile), every field audited (`description set`, `query
  limit max_operations = 1000 (applies at its next load)`, `... cleared`, `read-only`,
  `auto-load`).
- **Console:** `graphersal-server db info NAME`, `db set NAME description TEXT`, `db set NAME
  limit KEY VALUE`, `db set NAME limit KEY --clear` (offline or through a running server).
- `database.toml`'s `[limits.query]` now has a runtime writer (the settings change, under the
  registry's write lock; [Concurrent changes](../reference/server_directory.md#concurrent-changes)); every other rewrite still
  keeps the file's limits, so a hand edit survives.

## After a crash: the unclean-shutdown check, verify, repair and swap

A server killed by force (`kill -9`, an OOM kill, a power loss) left its databases' Stores
open and no word about it. The engine already replayed each Store's journal at its next open;
now the server finds out, checks and offers the way back
([Troubleshooting](../troubleshooting.md#a-server-was-killed-by-force)):

- **`server.open`**: the running server keeps the list of the databases it has open (loaded or
  loading), rewritten atomically on every load and unload and removed at a clean stop. `stop`
  on a stopped directory removes a stale `server.run` but never `server.open`.
- **The unclean-shutdown check.** A `serve` or `start` that finds a `server.open` or a stale
  `server.run` says so (`UNCLEAN SHUTDOWN` in the start block, an "Unclean shutdown" section, a
  log warning, the audit record `unclean shutdown of the last server (pid N) found`) and, in the
  background, loads every database the last server had open again (also without `auto_load`),
  keeps what the open of its Store did (clean close, journal commits replayed, the position, a
  torn tail cut) and verifies the open Store. Each result is logged and audited (`database 'x'
  checked: ok (...)`) and kept in the new `recovery.json`: `status` (also on a stopped
  server: what the next start will check), `GET /api/admin/server` and `GET
  /api/admin/recovery` (`uncleanShutdown`), the Databases tab (a box above the table), `db info`
  and the Database settings ("Damage and recovery") show the last unclean shutdown.
- **The state `maintenance`.** A database whose Store the engine opens in maintenance mode
  (damage found at the open), or whose verify finds damage under the damage policy
  `maintenance`, is served read-only with its damage report: `db list` (a Problems entry naming
  the repair), `status`, the listing's `state: "maintenance"` with `damage`, the Databases tab, the
  Database settings. This holds for every load, not only after a crash.
- **`db verify NAME | --all`** (`POST /api/admin/databases/<name>/verify`, `POST
  /api/admin/verify`, "Verify" and "Verify all" in the Databases tab): the engine's scrub of a
  Store (exit code 1 on damage).
- **`db repair NAME [--name NEW]`** (`POST /api/admin/databases/<name>/repair`, "Repair…"): the
  engine's repair into a NEW database (default `NAME-repaired`), never in place; the answer lists
  what was rebuilt, lost, diverged and never carried, and the copy is verified. Plain databases
  only (a layer or base: restore a backup).
- **`db swap NAME WITH --yes`** (`POST /api/admin/databases/<name>/swap {"with", "confirm":
  true}`, "Let it take the name…" after a repair): the repaired copy takes the damaged
  database's name, the damaged one moves to `trash/`; the name's grants, aliases, MCP settings
  and `database.toml` stay. Or keep both; or restore a backup (`db backups`, `db restore`).
- Audit records: `unclean shutdown ... found`, `database 'x' checked`, `database 'x' repaired
  into 'y'`, `database 'y' took the name 'x'`.

## Verify: progress, missing models named, the last result kept

- **Verify all shows its progress.** The Databases tab's "Verify all" verifies one database
  after the other (the per-database route) and shows `Verifying 3/10…` on its button; "Cancel"
  beside it stops before the next database. The result is one notice listing every database with
  problems and their problem lines.
- **A missing model blob is named as its model.** A verify that finds a missing blob of an
  embedding model says so: "the embedding model acme/tiny (blob f0ed7648) is missing", with the
  remedy (download or import the model on the Models tab, `graphersal-server models add SOURCE`,
  or `models add acme/tiny` when the shared models hold it). The answer's problems carry `kind`
  (`model` | `damage`), `model`, `blob`, `shared` and `remedy`; the console prints the
  `models add` command. Other missing blobs keep the generic text.
- **Missing models are not damage.** A verify whose only problems are missing model blobs has
  the new `verdict` `needs-model` (beside `ok` and `damaged`): the graph data is intact and the
  help names the model, not a repair. A plain database that is not loaded becomes `needs-model`
  (its `database.toml` marker set, as an import does), so adding the model gives it the blob back
  and makes it `unloaded`; a `needs-model` database that verifies clean is `unloaded` again.
  `db verify` still exits `1` for it (something must be done).
- **The last verify is kept** per database in `databases/<name>/verify.json` (also across a
  restart; also a verify that failed). The listing rows carry `lastVerify`, the Databases tab
  shows a small badge on a row whose last verify found something, and the Database settings'
  "Damage and recovery" shows it in one wording with the maintenance and `needs-model` states
  ("Last verify <time>: no problem found" / "…: the embedding model NAME is missing" / "…: N
  problems: its Store is damaged" / "Never verified: Verify … checks the whole Store"). This
  fixes the settings saying "No damage known" for a database whose verify had reported a missing
  model blob. `db info` shows the same lines.

## Server backups: back up the whole server, restore it on a new machine

One archive now holds the server itself
([Backups and Restore](../guide/backups.md#back-up-the-whole-server)):

- **`graphersal-server backup --dir DIR [--out FILE] [--with-databases]`** writes ONE ZIP
  (mode `0600`, through `FILE.part`): `server.toml`, `aliases.toml`, `access.toml` (users with
  their token hashes, roles and grants), `mcp.toml`, every database's `database.toml` (its
  settings: flags, description, limits, role and base), `models.json` (the shared models:
  repository, licence, blob hash) and `manifest.json` (format version, server version, time,
  the source directory's name, every file with its SHA-256, what was left out and why).
  Sessions, logs, `server.run`/`.lock`/`.open`, `recovery.json`, `tmp/`, `trash/`, `imports/`
  and `backups/` are never in it. `--with-databases` adds a fresh verified backup of every
  database (with its saved queries and backup jobs) and the shared model blobs: a full backup.
  Offline or through a running server, which copies its configuration files under their locks
  (one consistent state); `--token` works as for `db`.
- **`GET /api/admin/server-backup[?withDatabases=1]`** streams the same archive (the operator
  and admin users only; `everyone` of a server without access control is refused; audited), and
  the Backups tab has **"Download server backup"** (with or without the databases) beside the
  warning that the archive holds the token hashes.
- **`graphersal-server restore FILE --dir NEWDIR [--force-version]`** builds a NEW server
  directory (a missing or empty one only; never over a live directory): every checksum, the
  format version and the server version are checked before anything is written; the layout is
  owner only (`0700` directories, `0600` files); the databases come back from their embedded
  backups (bases before their layers), then the configuration. A database whose data the
  archive does not hold is skipped and reported, never half-registered; a failure leaves
  nothing behind. Users log in with their old tokens; sessions start afresh. The output ends
  with `serve --dir NEWDIR`. Recipe: "Move a server to a new machine".
- The archive is a secret ([Security Model](../guide/security.md#server-backups-are-secrets)).
- Not included: a scheduled server backup (the engine's backup jobs belong to one database);
  run `graphersal-server backup` from cron or a systemd timer.

## OpenAPI descriptions for HTTP clients

Programs can now generate HTTP clients for the server and its databases
([HTTP Clients and OpenAPI](../guide/http_clients.md)):

- **`GET /db/<name>/openapi.json`** (also `/db/<name>/api/openapi.json`) answers the database's
  HTTP API description (OpenAPI 3.1) patched for this server: `servers` is the URL the request
  came to (`[http] public_scheme`, the `Host`) plus `/db/<name>` (an alias keeps its own name),
  the security schemes `bearerAuth` (`Authorization: Bearer <user token>`) and `sessionCookie`
  (`gs_session`), global `security` with both (plus `{}` when anonymous reaches the name), the
  access layer's `401`/`404`/`409` on every operation, and `x-graphersal-access: read | query |
  write` on every operation (not filtered by the caller's level: a reader sees the writing
  operations, marked). It needs a read grant on the name and is answered also while the
  database is not loaded; anonymous without a grant gets `401` (no login redirect). Before,
  the engine's description named the dev server's `localhost:8080`, no security and none of
  the access layer's answers. The engine's part also gets what later graphersal-serve
  versions describe: the `409` of a read-only request on every writing route and the `403` of
  a path outside the backup root.
- **`GET /openapi.json`** (public) is a new, hand-written description of the server's own
  routes: the probes, login/logout, `/api/info`, `/api/databases` and the whole admin API
  (users, grants, aliases, databases with settings, verify/repair/swap, backups, restore,
  export, import, the inbox, models, runs, MCP, server, shutdown, server backup, recovery),
  with the revisions (`If-Match`, `409` with the current revision) and the error format; a
  test keeps it complete against the router's route tables.
- **`graphersal-server openapi --dir DIR [--db NAME] [--out FILE] [--server URL]`** writes
  either description without a running server (nothing written in `DIR`).
- `GET /api/info` names `openapi` and `databaseOpenapi`, `GET /api/databases` each row's
  `openapi`; the web UI links them ("OpenAPI" per database in My databases, "OpenAPI
  description" in each row's "…" menu of the admin's Databases tab).

## The web UI: one actions menu per row, notices that do not move the page

- **Databases tab without a horizontal scroll bar.** Every row action (Load or Unload…,
  Settings…, Runs…, Clone…, Backups…, Export…, Verify, Repair…, Promote to base…, Delete…; for
  an alias row Point to…, Rename…, Remove…) and the database's OpenAPI link (no longer in the
  Name column) sit behind ONE "…" button per row. The menu is keyboard accessible (a WAI-ARIA
  menu button: Enter or ↓ opens it, ↑/↓/Home/End move, Escape closes it and returns the focus),
  closes on a click outside, a scroll or a resize, and opens upward near the bottom of the
  window; an action that does not apply stays visible, greyed out, its tooltip says why. Long
  names and descriptions wrap. Checked at 1280 and 1024 pixels wide.
- **The line "HTTP clients: the server's API (OpenAPI) … Authorization: Bearer <token>" above
  the database table is gone**; the book covers it ([HTTP Clients and
  OpenAPI](../guide/http_clients.md)).
- **Default sort by name** for the Databases, Aliases and MCP tables until another column is
  chosen (a choice kept in the browser still wins).
- **Notices as toasts, on every tab.** The outcome of an action and the failure of an action
  started from a table row (or a switch) appear in a stack in the top-right corner, over the
  page (modelled on the playground's system journal notices): the page no longer jumps. An
  outcome hides itself after 6 seconds, a warning after 12, an error stays until closed; the
  time stops while the pointer or the focus is on the notice; the same notice again counts up
  instead of stacking; at most five at once. The persistent states stay in the page: a list that
  could not be read, the last unclean shutdown, the MCP status, a token shown once.
- **Form errors under the form's own button.** Every admin form (the grant form, the
  dialogs of Databases, Users and Models, Backups' "Show", "Back up now", the restore form and
  "Download server backup", Import, Export, the description and the query limits of Database
  settings) and the sign-in form show their error right under their submit button, not at the
  top of the page (an existing grant refused because the grants changed meanwhile, for
  example).
- **Users: the grant form's Database list** shows the aliases first (`cur → acme (alias)`),
  then the databases, each alphabetical in natural order, then "every database".
- **MCP: the switch-off question says what happens:** every MCP request is refused with `503`,
  also those of agents connected now; their sessions are not ended, and when MCP is switched on
  again they continue with the same session id and selected database, without connecting again;
  the HTTP API and the web pages are not affected. The tab's status text and the console's
  `mcp off` output say the same.
